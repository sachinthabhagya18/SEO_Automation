# Company SEO Connector 0.2.0

Install the generated ZIP in a disposable local/staging WordPress site. Settings → Company SEO selects standalone, external-owner or paused rendering. Known SEO conflicts suppress this renderer and never deactivate another plugin. Use a theme with core title-tag support and wp_head. Unknown hard-coded tags require developer inspection.

Implemented: locally stored post title/description/Open Graph text, canonical context defaults, core robots coordination, social text output, local editor metabox and authenticated read APIs. Version 0.2 adds allowlisted title/description preview/apply/status/restore, a transactional InnoDB unique-key ledger, expected-revision checks and conflict-aware restoration. Writes are off by default and only available in explicitly enabled local/staging WordPress environments, with a separate metadata capability and object edit checks. Production environments are rejected. No AI/network dependency during frontend rendering. Deactivation retains values and ledger history but removes rendered output. No destructive uninstall handler.

Reader role: `company_seo_reader` has only read/company_seo_read, without edit_users/edit_themes/install_plugins or content writes. Assign a dedicated user and WordPress Application Password. HTTPS is required except in explicitly local fixture mode. Public routes never expose draft/private/password-protected objects. Authorized editors with company_seo_read can inspect editable drafts through object checks. Cookies require standard REST nonce; use Application Passwords for machine requests.

The Company SEO Metadata Editor role has standard object-edit capabilities needed for metadata checks, plus separate company_seo_meta_write/company_seo_restore capabilities. Its mutating REST requests are restricted to this connector's allowlisted metadata routes; core body-edit REST requests are denied. Reader role permissions are unchanged. Settings → Company SEO enables metadata writes only for local/staging; the server enforces this even if options are manually modified. Django currently adds a stronger fixed-local-fixture-only write guard; installing the ZIP does not authorize live publishing.

Unsupported: term metadata, social images, structured data, breadcrumbs, custom canonical/robots overrides, custom sitemap exclusions, hreflang, body/content/price/stock edits and migration adapters. Core WordPress sitemaps remain owner. Elementor/Canvas and cache-provider compatibility are not yet tested. Transactional write support requires InnoDB for posts/postmeta/ledger. No exactly-once claim is made for arbitrary third-party hooks/cache behavior.

Build: `powershell -File scripts/package-plugin.ps1` from the repository root. Documentation/API output must accurately reflect capabilities; do not infer write support from a stored metadata field.
