1. Product objective and operating context
We build and maintain WordPress websites using both custom-coded themes and Elementor. We need one internal platform to manage SEO for multiple websites, each with its own dashboard, staff permissions, business knowledge, reference websites, keyword strategy, automation policies, history, and results.

The product must support the lifecycle: onboard a website; connect WordPress; collect evidence; research supplied reference/competitor websites; discover and cluster keyword candidates; audit; prioritize; generate grounded changes; review; publish supported changes; verify rendered output; recover when necessary; track search performance and conversions.

The user has Docker installed on a Windows development computer and uses VS Code. Detect the actual shell and Docker availability. Provide PowerShell-compatible onboarding alongside container commands. Do not assume host Python, PHP, PostgreSQL, Redis, or Node are installed. Prefer containers for consistent execution. Never reset or overwrite unrelated repositories, Docker volumes, databases, or existing user work.

Initial product is an internal company tool, not a public SaaS signup service. Architect site-scoped data cleanly for future expansion. Do not implement billing or public registration unless requested. Use Asia/Colombo as the default display/schedule timezone, store timezone-aware timestamps in UTC, and permit per-site timezones.
2. Fixed architecture choices
- Backend: a supported stable Django release plus Django REST Framework.
- UI: Django Templates + compiled Tailwind CSS + Alpine.js. No Vue, React, Next.js, or duplicate frontend frameworks in this version.
- PostgreSQL: application persistence; do not silently substitute SQLite for integration testing.
- Celery + Redis: asynchronous jobs, controlled retries, locks and temporary caches. PostgreSQL is authoritative for business job state.
- n8n: external workflow coordination and schedules through authenticated Django APIs. n8n must not write directly into application database tables.
- Docker Compose: reproducible local services, health checks and persistent volumes.
- WordPress PHP plugin: our own standalone SEO rendering and connector plugin. Yoast, Rank Math and paid SEO plugins are NOT prerequisites.
- AI: a provider adapter interface; implement at least one live provider end to end, initially Gemini unless project credentials/preferences indicate another. Use current official SDK documentation. Add provider interfaces for Claude/OpenAI without pretending unimplemented adapters work. Model IDs must be configuration values, not claims about an eternally latest/best model.
- AI workflow: implement a checkpointed LangGraph flow for evidence -> draft -> validation -> review state. Celery owns executing jobs; LangGraph owns only the inner AI workflow state, not scheduling or arbitrary publishing. Establish a simple deterministic vertical slice before adding orchestration. LangChain components are optional; CrewAI is not a dependency.
- Crawling: Python HTTP client + HTML parser; optional isolated Playwright worker for selected JS-rendered pages. Do not render every page through a browser by default.
- Charts: a small maintained chart library with accessible table alternatives.
- Persistence for uploaded reports/snapshots: persistent local volume initially, storage interface for S3-compatible storage later.
Verify compatible versions using official documentation, pin dependencies and images, commit lockfiles, and record the tested compatibility matrix. Do not use floating latest tags for reproducibility.

Coordinate core canonical and robots behavior so there are no duplicates or conflicting directives. Do not insert tags using client-side Alpine/JavaScript. 7.4 Proposed API contract
Use a versioned namespace such as company-seo/v1 and document actual responses with examples:
- GET /capabilities: plugin/WP versions, renderer mode, builder/adapters, allowed operations.
- GET /pages: paginated authorized content inventory.
- GET /pages/{id}/seo: current values, effective values, provenance and revision/hash.
- GET /pages/{id}/content-map: supported editable fields and references.
- POST /changes/preview: validate proposed changes and return diff without writes.
- POST /changes/apply: apply a previously approved change payload using expected revision/hash and idempotency key.
- GET /changes/{change_id}: recover the status/result after a timeout.
- POST /changes/{change_id}/restore: conflict-aware restoration of supported fields.
- GET /health: authenticated diagnostics; keep any public health output minimal.
Never expose arbitrary file read/write, SQL, PHP evaluation, shell execution or arbitrary post-meta mutation endpoints.

Store a durable idempotency ledger with a unique request identifier and payload hash. Same key/same payload returns the prior result; same key/different payload fails. Handle concurrent retries with database uniqueness/locking; do not claim exactly-once execution merely because a cache lock exists. On ambiguous network failure, reconcile via change status before retrying.

9. Audit engine and SEO feature scope
Use deterministic checks for measurable facts; reserve AI for interpretation and drafting. Store issue code, severity, evidence, URL, detected time, rule version, remediation, confidence where relevant, status and responsible person.

Technical checks: status codes; redirects/chains/loops; broken internal resources/links; crawl scope; robots directives; noindex/canonical conflicts; sitemap inventory differences; HTTPS/mixed content; missing/duplicate titles/descriptions; heading structure; image alt context and size; schema parsing/consistency; internal-link coverage; pagination; language mappings; parameter/faceted crawl traps; mobile/performance diagnostics.

Orphan detection compares discovered links with independent inventories such as WordPress/sitemaps. Missing data cannot prove orphanhood. Do not equate robots blocking with guaranteed deindexing. Multiple headings, short descriptions or word counts need contextual rules rather than universal ranking claims. Decorative images may correctly use empty alt text. Avoid keyword stuffing and mechanical keyword-density targets.

Content features: primary keyword map, briefs, topic clusters, gap analysis, update suggestions, readability/context review, factual checks against approved sources, internal-link proposals, image-alt drafts, structured-data proposals and multilingual drafts. Local SEO: business identity/contact consistency, location pages, supported business profile integration or documented manual tasks. Off-page SEO: imported/provider backlink evidence, mention tracking, outreach drafts and task management. Do not auto-buy links, mass-comment or send outreach without authorization. Lack of a data provider must appear as unavailable, not zero backlinks.

E-commerce: page/product/category support and optional WooCommerce adapter with actual inventory/price source, canonical/variant rules and field-specific permissions. Never rewrite prices/stock or commercial policies through ordinary SEO drafts.

International SEO: country/language targeting, reciprocal mapping validation, translation ownership and multilingual-plugin capability checks. Build extension points and clearly track any unimplemented provider adapters.
10. Health scoring and prioritization
Call the internal score SEO Health Score, not a Google score or ranking prediction. Use a versioned deterministic weighted rubric, initially technical crawlability 30%, on-page checks 25%, internal architecture 20%, schema consistency 10%, performance checks 15%, subject to documented applicability.

Normalize only across applicable observed checks, show coverage and data freshness, and display unknown/not-applicable separately. A site with very few observed checks must not receive a misleading high-confidence score. Critical blockers remain visible regardless of aggregate score. Keep AI qualitative assessments separate.

Prioritize issues using a transparent heuristic of severity, affected important pages, observed traffic/business relevance and effort. Do not invent an expected ranking uplift. A score improvement indicates rule compliance, not proven traffic growth.

AI tasks: keyword expansion/clustering, intent classification, brief generation, title/description proposals, supported content rewrites, internal-link suggestions, factual schema drafts and evidence-based summaries. Avoid unnecessary model calls for deterministic audit checks.

Return typed, validated JSON using Pydantic-compatible schemas. Each proposal includes site/page identity, change type, current value/hash, proposed value, reason, source IDs, unsupported-fact flags and review requirement. Schema compliance is not truth verification. Limit output size and HTML allowlists. Never let a model choose arbitrary site IDs, credentials, shell commands or write operations.

Treat crawled content and uploaded reference documents as untrusted data. They must not override system instructions, permissions, budgets, target sites or publishing policies. Strip/contain executable content; do not expose credentials to prompts. Distinguish business facts from quoted competitor claims.

Use bounded retries for invalid outputs, provider timeouts, rate limits and transient errors. Enforce site/job/monthly budgets and maximum workflow steps. Cache by content hash plus business-profile/prompt/model version; invalidate when relevant context changes.

Implement durable LangGraph checkpoints only after the deterministic flow works. Human review is a persisted pause/state, not a worker left running for days. Django approval state is authoritative; graph resume revalidates it and cannot bypass the publisher service. Avoid two independent approval sources. An AI reviewer never substitutes for policy-required human approval.
12. Approval, publication, verification and recovery
Modes: read_only, draft_only, approval_required (default), selected_auto_actions. Automatic modes are scoped to site, field type, budget and policy version. Code changes, deletion, URL/slug changes, redirects, canonical/robots changes and bulk content replacement need explicit high-risk approval. Do not let a schedule silently escalate privileges.

State model: proposed -> validated -> pending_review -> approved/rejected -> queued -> applying -> applied_pending_verification -> verified/verification_failed. Include stale_conflict, retryable_failure, ambiguous_remote_result, cancelled and restoration states as needed. AI failure never becomes a successful publish.

Approval binds to an immutable payload hash, target, base revision and policy version. Editing a draft invalidates its old approval. Before publication, recheck permission, policy, current remote hash, site pause state and renderer/adapter capability. Use per-page execution coordination and durable remote idempotency. A transaction in Django cannot atomically roll back a remote WordPress request; implement recovery explicitly.

Snapshots capture fields, prior metadata, content/document version, relevant renderer ownership and all values needed for supported restoration. Show a readable diff and affected-page impact before approval.

After apply, fetch the actual public page (with bounded cache refresh/retry), verify single intended tags, canonical/robots, selected content and no obvious error status. API 200 is not proof that the public page changed. Record delayed cache propagation separately from a permanent failure. Never mark Google ranking/indexing as verified just because HTML changed.

Rollback restores only supported fields and checks that the current state matches the applied change. If another editor changed content later, require a conflict resolution path instead of overwriting it. Provide emergency pause, per-site kill switch, rollback history and a bulk operation kill switch. Test partial failures and interrupted publication.
13. Search performance and analytics
Integrate Google Search Console OAuth with property selection/permission checks. Integrate GA4 property selection and documented conversion/key-event mapping for enquiries, bookings and relevant clicks. Never equate every visit or button click with a confirmed sale. Configure organic channel reporting and display tracking gaps.

Use PageSpeed/Lighthouse for lab diagnostics; use the current supported CrUX API path for field data where available. Verify current API responses instead of assuming PSI always includes all field data. Keep lab and field scores separate; insufficient real-user data is unavailable. Track mobile/desktop, measurement timestamp, page/origin scope and LCP/INP/CLS when available.

Compare periods with consistent filters and note seasonality/data delay. Annotate changes on charts; do not claim causation from before/after traffic alone. Optional SERP tracking and backlink APIs require separate provider configuration and costs.

Workflow exports contain no passwords, application passwords, OAuth refresh tokens, actual secrets or user-specific credential IDs. Make required credential bindings explicit. Bind development UIs to localhost by default; keep databases/Redis internal unless a documented local debug profile is used. Use health checks and startup readiness, not sleeps alone.

Optional WordPress test profile must include WordPress plus its compatible MySQL/MariaDB service; WordPress does not use the app PostgreSQL database by default. Add a WP-CLI helper if useful. Fixtures should test a small custom theme and Elementor when its installation is available. Elementor Pro is optional and must not be assumed licensed.

Provide idempotent scripts for preflight, environment generation, docker compose build/up, migrations, bootstrap admin, fixtures and service checks. Generate strong local secrets without printing them into logs. Do not create a fixed admin/admin account. Provide a safe one-time invitation/password setup mechanism. Clearly distinguish initial database initialization from migrations and upgrades.

The PostgreSQL Docker init environment runs on first initialization only; do not promise changing .env recreates existing users/databases. Never use docker compose down -v as a routine troubleshooting step. Provide logical backup/restore commands and verify restoration in a disposable environment.

Persist PostgreSQL, n8n data/encryption key and application uploads. Redis business tasks must recover via durable job records if queue messages are lost. Do not mount the Docker socket into app/n8n containers. Run with least practical privileges and do not expose secrets in image layers.

Crawl SSRF protection must block loopback, private/link-local addresses, metadata endpoints, unsafe schemes and unsafe redirects, including DNS rebinding defenses. Explicit local test domains may be allowlisted only in isolated development mode; never globally disable the protection for production. M4 — AI/review/publication vertical slice: one live AI provider adapter, grounded title/description drafts, validated diff, approval, plugin write, public verification and rollback. Acceptance: authorized flow succeeds; stale edits/duplicate jobs fail safely; no secret reaches the model.
